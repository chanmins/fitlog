## 1. 판단: 넣습니다. 단, 흔한 방식으로는 안 넣습니다

넣자는 쪽입니다. 다만 "식단 관리" 라는 말을 들었을 때 대부분이 떠올리는 것 —
아침·점심·저녁을 나누고, 음식을 검색해서, 그램을 입력하고, 칼로리·탄단지가
쌓이는 화면 — 그건 만들면 안 됩니다. 이유가 셋입니다.

**첫째, 그 기능은 사람을 잃는 기능입니다.** 칼로리 기록은 하루 3~5회, 매번
30초~1분을 요구합니다. 운동 기록은 주 3~4회 헬스장에서만 열면 되지만, 식단은
매일 세 번입니다. 요구량이 5배인데 그 대가로 돌려주는 게 "어제보다 200kcal 적게
먹었네" 라는, 그날 하루의 오차 범위 안에 있는 숫자입니다. 사람들은 2주쯤 하다가
한 끼를 빠뜨리고, 빈 칸이 생기고, 그 다음부터 안 엽니다. **문제는 그 사람이 식단
탭만 안 여는 게 아니라는 겁니다.** 앱 전체가 "내가 실패한 것" 이 되어 운동 기록도
같이 멈춥니다. 잘 돌아가던 기능이 새 기능 때문에 죽는 게 가장 나쁜 결과입니다.

**둘째, 이 앱의 원칙과 정면으로 부딪힙니다.** `renderBalanceCard()` 위에 이미
적혀 있는 말입니다 — *"세트 합계는 '얼마나 들었나' 에 답하는데, 그건 손쓸 수 없는
숫자다."* 그래서 홈 화면을 주간 세트 수 대신 부위 균형으로 바꿨습니다. 휴식
타이머도 같은 이유로 기본 꺼짐입니다 — *"쉬는 시간을 시계로 재지 않는 사람이
대부분인데 화면 아래를 차지한다."* 이 두 결정을 내린 앱이 "오늘 1,847kcal 섭취"
를 홈에 띄우면 앞뒤가 안 맞습니다. 1,847이라는 숫자를 보고 내일 뭘 다르게 할지
말할 수 있어야 하는데, 못 합니다. 애초에 그 숫자의 오차가 ±20% 입니다(눈대중
그램, 조리법, DB 편차).

**셋째 — 그리고 이게 진짜 이유입니다 — 칼로리는 이미 알고 있습니다.**
FitLog 에는 `metrics` 저장소가 있고 거기에 몸무게가 날짜별로 쌓여 있습니다.
2주치 몸무게 기울기는 그 사람이 잉여를 먹는지 결손을 먹는지를 **어떤 음식 DB보다
정확하게** 말해 줍니다. 체중이 2주에 +0.4kg 이면 잉여입니다. 그 사람이 입력한
칼로리 합계가 뭐라고 하든 저울이 이깁니다. 그러니 칼로리를 세는 건 이미 가진
답을 훨씬 나쁜 방법으로 다시 구하는 일입니다.

저울이 **말해 주지 못하는 것이 딱 하나** 있습니다. 같은 체중 변화를 근육으로
채웠는지 지방으로 채웠는지 — 그건 단백질을 충분히 먹었느냐로 갈립니다. 그리고
단백질은 세기가 쉽습니다. 하루에 먹는 단백질원은 보통 4~6개고, 대부분 같은
것들의 반복입니다.

> **결론: 몸무게(이미 있음) + 단백질(새로 추가) = 식단 관리 끝.**
> 칼로리·탄수화물·지방은 만들지 않습니다.

## 2. 제품 정의

### 2.1 목표 단백질

프로필에 이미 성별·나이·키·몸무게가 있습니다(`sanitizeProfile`). 여기에
몸무게만 있으면 목표가 나옵니다.

```
목표(g) = 최근 몸무게(kg) × 계수
```

| 모드 | 계수 | 화면 표기 |
|---|---|---|
| 유지 | 1.6 | 근육 유지·성장에 필요한 최소선 |
| 증량 | 1.8 | 기본값 |
| 감량 | 2.2 | 결손 중에는 근손실을 막느라 더 필요합니다 |

1.6~2.2 g/kg 는 저항운동 인구 메타분석의 표준 범위입니다(그 위로는 추가 이득이
관찰되지 않습니다). 소수점은 버리고 5g 단위로 반올림해서 보여 줍니다 — `120g`
과 `118.4g` 중 사람이 따라갈 수 있는 건 앞쪽입니다.

몸무게가 없으면? 목표를 지어내지 않습니다. 카드가 "몸무게를 먼저 기록해
주세요" 로 뜨고 기존 `add-weight` 흐름을 그대로 엽니다. **없는 값으로 추정한
목표를 보여 주는 것보다 목표가 없는 편이 낫습니다.**

### 2.2 기록 흐름 — 목표는 "3초, 3탭"

홈 카드의 `+` → 시트가 올라옵니다.

```
┌─────────────────────────────┐
│  오늘 단백질          82/120g│
│  ●●●●●●●○○○  68%             │
├─────────────────────────────┤
│  자주 먹는 것                │
│  [닭가슴살 100g +23] [계란 +6]│
│  [프로틴 1스쿱 +24] [우유 +7] │
│  [두부 반모 +12]  [참치캔 +26]│
├─────────────────────────────┤
│  [ 🔍 음식 찾기 ]  [ 직접 g ]│
├─────────────────────────────┤
│  오늘 먹은 것                │
│  계란 2개  12g            ✕  │
│  닭가슴살 100g  23g       ✕  │
└─────────────────────────────┘
```

- **칩 하나 = 1탭 = 기록 끝.** 시트가 닫히지 않아서 연달아 누를 수 있습니다.
  계란 3개면 계란 칩을 3번 누릅니다(수량 입력 화면 없음 — 그게 3초를 30초로
  만듭니다).
- **자주 먹는 것** 은 사용 횟수·최근순 정렬입니다(`routines.usedAt` 과 같은
  방식). 일주일만 쓰면 이 6칸이 그 사람의 실제 식단이 되어서 검색을 거의 안
  쓰게 됩니다. 이게 이 설계의 전부입니다.
- **직접 g** 는 숫자만 넣는 탈출구입니다. 외식·집밥처럼 이름 붙일 수 없는
  끼니용. 기존 `repsPicker` 넘패드 시트를 그대로 재사용합니다.
- **끼니 구분 없음.** 아침/점심/저녁/간식을 나누는 건 입력을 4배로 만들면서
  단백질 총량에는 아무 정보도 더하지 않습니다. (타이밍이 중요하다는 주장이
  있지만, 총량이 맞은 다음의 이야기입니다.)

### 2.3 평가는 '하루' 가 아니라 '주 평균' 으로

**이 기획에서 가장 중요한 한 줄입니다.**

하루 목표로 평가하면 링을 못 채운 날이 곧 실패입니다. 아무리 성실한 사람도
주에 1~2일은 놓칩니다(회식, 아픈 날, 그냥 잊은 날). 실패 표시가 두 번 쌓이면
앱을 안 엽니다 — 1절에서 말한 그 이탈이 여기서 시작됩니다.

그래서 **성과 판정은 최근 7일 평균으로만** 합니다.

- 홈 링은 오늘 진행률을 보여 주되, 못 채웠다고 빨강으로 바꾸지 않습니다.
  회색은 "아직" 이지 "실패" 가 아닙니다.
- 기록이 없는 날은 평균에서 **뺍니다**(0으로 세지 않습니다). 안 적은 날을 0g
  먹은 날로 세면, 기록을 빠뜨릴수록 숫자가 나빠져서 "이제 와서 다시 시작해도
  망했다" 가 됩니다. 기록한 날만으로 평균을 내고 "5일 중 4일 기록" 을 같이
  적습니다.
- 연속 기록(streak) 을 붙이지 않습니다. streak 은 끊기는 순간 그만두게
  만드는 장치입니다. 운동 쪽 streak 은 이미 있으니 그걸로 충분합니다.

### 2.4 화면별 배치

| 위치 | 무엇 | 조건 |
|---|---|---|
| 홈 | 단백질 링 카드 (오늘 + 주 평균 한 줄) | 기능 켬 |
| 홈 | `+` 버튼 → 기록 시트 | 〃 |
| 히스토리 | 단백질 주간 카드 — 7일 막대 + 목표선 | 기록 3일 이상 |
| 히스토리 | 몸무게 카드에 단백질 겹쳐 보기 토글 | 둘 다 14일 이상 |
| 설정 | `식단 기록` 스위치 + 목표 모드(유지/증량/감량) | 항상 |

**기본값은 꺼짐입니다.** 휴식 타이머와 같은 판단입니다 — 홈 화면 한 칸은
비싸고, 식단을 기록할 생각이 없는 사람에게 그 칸은 매일 보이는 잔소리입니다.
설정에서 한 번 켠 사람에게만 보입니다.

### 2.5 코칭 한 줄 (v2)

몸무게 추세와 단백질을 같이 보면 실제로 손쓸 수 있는 말이 나옵니다.

| 체중 2주 기울기 | 주 평균 단백질 | 한 줄 |
|---|---|---|
| +0.2~0.5kg/주 | 목표 이상 | 증량이 잘 되고 있어요 |
| +0.2~0.5kg/주 | 목표 미만 | 체중은 느는데 단백질이 부족해요 — 늘어나는 쪽이 근육이 아닐 수 있어요 |
| 거의 변화 없음 | 목표 이상 | 유지 중입니다. 늘리려면 더 먹어야 해요 |
| -0.3kg/주 이상 감소 | 목표 미만 | 결손 중에 단백질이 부족합니다 — 근손실 위험이 가장 큰 조합이에요 |

이건 v1 에는 넣지 않습니다. 데이터가 2주 쌓인 뒤에야 말이 되는 기능입니다.

### 2.6 안전 문구

설정 화면 하단에 한 줄. **단백질 목표는 건강한 성인의 저항운동 기준입니다.
신장 질환이 있거나 임신 중이라면 의사와 상의하세요.** 화면마다 반복하지
않습니다.

## 3. 음식 데이터 — 어디서 채우나

물어보신 부분입니다. 세 가지를 놓고 봤습니다.

### 옵션 1. 식약처 식품영양성분DB (공공데이터포털)

- **장점**: 무료, 한국 음식 커버리지 최고, 10만 건 이상, 신뢰도 높음.
- **문제 (a) 용량**: 10만 건 × 최소 필드만 잡아도 3~5MB 입니다. 지금 앱은 정적
  호스팅 + 서비스워커로 **100% 오프라인** 이 돌아갑니다(`sw.js` ASSETS). 5MB
  를 앱 셸에 넣으면 첫 로딩이 무너지고, 서버 검색으로 빼면 헬스장 지하에서
  안 됩니다.
- **문제 (b) 검색 UX**: "닭" 을 치면 300개가 나옵니다. `닭가슴살,생것`,
  `닭가슴살,삶은것`, `닭가슴살,구운것`, `닭가슴살(수입산)`… 고르는 데 20초
  걸리면 3초 설계가 무너집니다. 큰 DB 는 항상 이 문제를 갖고, 그래서 상용
  앱들이 바코드·사진 인식에 돈을 씁니다.
- **문제 (c) 라이선스**: 출처 표기 의무와 갱신 주기 관리가 붙습니다.

→ **A안에는 과합니다.** 나중에 칼로리·탄단지까지 갈 때 다시 꺼낼 카드입니다.

### 옵션 2. 내장 소형 리스트 40~60개 ← **추천**

`exercises.js` 와 정확히 같은 방식으로 `foods.js` 를 하나 더 둡니다.

- **왜 40개로 충분한가**: 단백질만 세기 때문입니다. 한국 헬스인이 실제로 먹는
  단백질원은 놀랍도록 좁습니다 — 닭가슴살/닭다리, 소·돼지 몇 부위, 계란,
  참치캔, 연어, 흰살생선, 두부, 콩, 우유, 그릭요거트, 치즈, 프로틴, 그리고
  밥·면·빵의 딸린 단백질. 40개면 실사용의 90% 를 덮습니다. 나머지 10% 는
  '직접 g' 또는 '내 음식 추가' 한 번이면 영구히 자기 목록에 남습니다.
- **용량**: 4KB 안쪽. 오프라인 100% 유지. 검색이 즉시.
- **정확도**: 100g 당이 아니라 **실제 먹는 단위**(계란 1개, 캔 1개, 1스쿱,
  두부 반 모)로 적어야 3초 입력이 성립합니다. 부록 A 가 초안입니다.

### 옵션 3. 사용자 등록만

첫날의 벽이 너무 높습니다. 아무것도 없는 화면에서 "닭가슴살, 100g, 23g" 을
직접 쳐 넣어야 시작됩니다. 다만 옵션 2 와 **결합하면** 완성입니다 — 40개로
시작하고, 없는 건 추가하고, 추가한 건 다음부터 칩으로 나옵니다.

### 결론

**옵션 2 + 3.** 내장 40개 + 사용자 음식 추가 + 사용 빈도 기반 자동 정렬.
식약처 DB 는 v3 에서 칼로리를 넣기로 결정할 때 재검토합니다.

부록 A 의 수치는 구현 시 식약처 DB 로 한 번 대조하는 걸 전제로 한 초안입니다.

## 4. 구현 명세

### 4.1 데이터 모델

**새 저장소 두 개.** `metrics`(몸무게)는 **손대지 않습니다** — 1년치 몸무게가
들어 있는 곳에 스키마 변경을 얹을 이유가 없습니다.

```js
// diet — 날짜가 키. sessions 와 같은 모양.
{
  date: "2026-09-02",
  items: [
    { id: "f-egg",  name: "계란",     g: 6,  qty: 2, at: 1788228000000 },
    { id: null,     name: "직접 입력", g: 30, qty: 1, at: 1788231000000 }
  ],
  totalG: 42        // items 에서 파생되지만 저장합니다 — 히스토리에서 30일치를
                    // 그릴 때 매번 재계산하지 않으려고. 쓰기 시점에 갱신.
}

// foods — 사용자가 추가한 음식. routines 와 같은 모양.
{ id: "uf-1788228000000", name: "회사 앞 도시락", g: 28, usedAt: 1788228000000, useCount: 12 }
```

`FOODS`(내장 40개)는 코드 상수라 저장하지 않습니다. 사용 빈도만 `localStorage`
에 `{foodId: count}` 로 둡니다 — 이 기기의 취향이지 계정 데이터가 아니고,
날려도 다음 주면 다시 쌓입니다.

### 4.2 `db.js`

```js
const DB_VERSION = 4;      // 3 → 4  ⚠️ 이 파일 맨 위 주석이 경고하는 그 지점
```

`createStores()` 에 두 줄 추가:

```js
if (!db.objectStoreNames.contains("diet"))  db.createObjectStore("diet",  { keyPath: "date" });
if (!db.objectStoreNames.contains("foods")) db.createObjectStore("foods", { keyPath: "id" });
```

`open()` 안의 **'빠진 저장소 복구' 검사에도 두 이름을 반드시 추가**합니다.
빠뜨리면 v4 로 올라간 기기에서 복구 로직이 영원히 못 도는 게 아니라, 반대로
기존 검사만 통과해 놓고 `diet` 없는 DB 를 그대로 씁니다 → 모든 식단
트랜잭션이 `object stores was not found` 로 터집니다.

추가 함수(기존 metrics/routines 와 같은 꼴):

`pullAll()` 에 `dietCol.get()` 를 `Promise.all` 로 추가하고 반환에
`diet`, `foods` 를 얹습니다. `deleteAccountAndData()` 의
`deleteAllDocs("sessions")` 옆에 `deleteAllDocs("diet")` 를 **반드시**

**왜 `diet` 는 하위 컬렉션인가**: `metrics` 는 하루 40바이트라 문서 하나에

230KB, 여기에 다른 필드까지 얹으면 Firestore 문서 1MB 한계에 몇 년 안에
닿습니다. 한계에 닿는 날 조용히 쓰기가 실패합니다. 처음부터 세션과 같은
구조로 두면 그 날이 오지 않습니다.

**목표 계산**

```js
const PROTEIN_COEF = { maintain: 1.6, bulk: 1.8, cut: 2.2 };
function proteinTarget() {
  const last = state.metrics[state.metrics.length - 1];
  const kg = last ? last.weightKg : Number(state.profile?.weightKg) || 0;
  if (!kg) return 0;                                   // 0 = "몸무게 먼저"
  return Math.round(kg * PROTEIN_COEF[dietGoalMode()] / 5) * 5;
}
```

**주 평균** — 기록이 없는 날은 분모에서 제외:

```js
function proteinWeekAvg() {
  const days = lastNDates(7);                          // 기존 getWeekDays 계열 재사용
  const rows = days.map(d => state.diet.find(x => x.date === d)).filter(r => r && r.totalG > 0);
  if (!rows.length) return null;
  return { avg: Math.round(rows.reduce((a,r)=>a+r.totalG,0) / rows.length), logged: rows.length };
}
```

**액션**: `open-diet` · `close-diet` · `diet-add`(data-food) · `diet-add-manual` ·
`diet-remove`(data-idx) · `add-my-food` · `toggle-diet` · `set-diet-goal`

**저장 경로** — 기존 규약과 동일하게 즉시 저장 + 클라우드는 뒤따라감:

```js
async function dietAdd(food, grams) {
  const row = state.dietToday || (state.dietToday = { date: todayISO(), items: [], totalG: 0 });
  row.items.push({ id: food?.id ?? null, name: food?.name ?? '직접 입력',
                   g: grams, qty: 1, at: Date.now() });
  row.totalG = row.items.reduce((a, i) => a + i.g, 0);
  upsertDietDay(row);                         // state.diet 갱신
  await WorkoutDB.putDiet(row);               // 실패하면 saveBroken 경고 (기존 흐름)
  cloudSync(() => Cloud.saveDietDay(row));
  bumpFoodUse(food);
  renderDietSheetOnly();                      // ← 전체 render() 금지
}
```

> ⚠️ **전체 `render()` 를 부르지 마세요.** 이 앱의 `render()` 는 `#app` 을
> innerHTML 로 통째로 갈아 끼웁니다. 시트가 열린 채로 칩을 연타하는 상황에서
> 매번 통째로 다시 그리면 스크롤 위치와 포커스가 날아갑니다 — 휴식 타이머를
> `<body>` 직속 노드로 뺀 것과 정확히 같은 이유입니다. 시트 안의 링·합계·
> 목록만 직접 DOM 갱신하는 좁은 함수를 따로 둡니다.

### 4.7 백업 호환

`exportAll()` → `version: 3`, `diet`·`foods` 추가.
`importAll()` 은 `metrics`/`routines` 와 **같은 원칙**:

- 검증: `date` 는 `/^\d{4}-\d{2}-\d{2}$/`, `items` 는 배열, `g` 는 0 < g ≤ 500.
